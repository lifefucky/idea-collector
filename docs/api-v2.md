## Спецификация бэкенда Mini App «Карман» v2

Этот документ фиксирует, что меняется и **что не меняется** в HTTP API и моделях данных при переходе на новый фронтовый референс. Цель — подтвердить, что все новые UI‑элементы работают на уже существующих ручках и сущностях.

---

## 1. Сущности и границы ответственности

### 1.1. Идеи

- Хранение — таблица `ideas` в `IdeaStore` (`src/idea_collector/db.py`):
  - поля уже покрывают:
    - идентификатор (`id`);
    - owner‑ключ (`owner`);
    - заголовок/лейбл (`label`);
    - полный текст (`copy`);
    - полку (источник идеи) и служебные поля LLM‑обогащения.
- В v2:
  - **нет новых полей** для:
    - People / пользователей;
    - статусов Inbox/«обработано»;
    - аналитики/счётчиков.

### 1.2. Источники (Sources)

- Хранение — таблица `sources` в `SourceStore`:
  - `id`, `owner`, `title`, `url`.
- В v2:
  - **нет новых полей** для:
    - аббревиатур;
    - частоты использования (`часто`);
    - описаний «Зачем».
  - Все подсказки (чипы, подписи `полка`, алгоритм аббревиатур) живут только на фронте.

### 1.3. Оператор и owner‑ключ

- Оператор — один Telegram‑аккаунт (см. `Config.operator_telegram_id`).
- Owner‑ключ формируется в `web.py`:
  - при `initData == "dev"` и локальном хосте:
    - `owner = f"local:{operator_telegram_id}"`;
  - при валидном Telegram `initData`:
    - `owner = f"tg:{user.id}"`.
- В v2:
  - схема owner‑ключа **не меняется**;
  - нет многопользовательских карманов, ролей и т.п.

## 2. HTTP API (контракты)

### 2.1. HTML Mini App

- `GET /`:
  - отвечает `index.html` из `webapp_index_path()` с подстановкой `__IDEAS_COUNT__`;
  - для локального превью:
    - count берётся из `store.count_for_owner(local_owner)`;
  - для Telegram:
    - при валидном `initData` — из `store.count_for_owner(owner)`;
    - при ошибке auth — общий `store.count()`.
- В v2: поведение остаётся прежним; фронт отвечает за то, как это число отображается.

### 2.2. Счётчик

- `GET /api/count`:
  - вход:
    - заголовок `Authorization: tma <initData>`;
  - выход:
    - `{ "count": <int> }` — количество идей в кармане текущего owner:
      - локальный режим → `local:<operator_id>`;
      - Telegram → `tg:<user.id>`.
  - при отсутствии или ошибке `initData`:
    - HTTP 401 / 403 + `{ "error": "…" }` — **в отличие от `GET /`, нет fallback на глобальный счётчик.**
- Фронт может продолжать использовать этот эндпоинт только на сервере (в `index.html`) или для служебных проверок, но не в рантайме Mini App; для пользователя источник правды — HTML `/`.

### 2.3. Идеи

- `GET /api/ideas`:
  - вход:
    - заголовок `Authorization: tma <initData>`;
  - выход:
    - `{ "count": <int>, "shelves": [ { "name": str, "ideas": [ { "id": int, "label": str, "copy": str } ] } ] }`.
- `POST /api/ideas`:
  - вход JSON:
    - `{ "text": "..." }`;
  - поведение:
    - проверка `initData` и оператора;
    - insert в `ideas` с owner‑ключом;
    - постановка в очередь LLM‑обогащения;
  - выход:
    - `{ "count": <int>, "label": str, "copy": str, "shelf": str }`.
- `DELETE /api/ideas/{id}`:
  - вход:
    - заголовок `Authorization: tma <initData>`;
    - `id` — идентификатор идеи внутри кармана оператора;
  - поведение:
    - проверка, что идея принадлежит owner;
    - удаление, пересчёт `count`;
  - выход:
    - при успехе — HTTP 200 + `{ "count": <int> }` (и/или пустое тело; текущий контракт остаётся);
    - при отсутствии — 404;
    - при ошибке — 5xx.

**Важно для v2:**

- Из API не появляются новые поля:
  - нет `tone`, `short`, People и т.п.;
  - вся визуальная информация (цвет карточки, короткие названия полок) выводится из уже имеющихся `shelf.name` и клиентской логики.

### 2.4. Sources

- `GET /api/sources`:
  - вход:
    - заголовок `Authorization: tma <initData>`;
  - выход:
    - `{ "sources": [ { "id": int, "title": str, "url": str } ] }` только для текущего owner.

- `POST /api/sources`:
  - вход JSON:
    - `{ "title": str, "url": str }`;
  - поведение:
    - валидация `initData`;
    - простая валидация URL (минимум — не пустая строка), остальные проверки — ответственность фронта;
    - insert в `SourceStore` с owner‑ключом;
  - выход:
    - `{ "id": int, "title": str, "url": str }` — созданный источник.

- `DELETE /api/sources/{id}`:
  - вход:
    - заголовок `Authorization: tma <initData>`;
  - поведение:
    - удаление источника, если принадлежит owner;
  - выход:
    - при успехе — 200;
    - при отсутствии — 404;
    - при ошибке — 5xx.

**Важно для v2:**

- Частота использования источника (`часто`), короткие коды (`PH`, `YC`), подписи `полка` — **не добавляются** в API:
  - все примеры и аббревиатуры живут на фронте либо как статический список, либо на основе `title`.

## 3. Telegram‑интеграция и auth

- Авторизация Mini App и API:
  - вся логика остаётся в `auth.py` + `web.py`:
    - чтение `initData` из заголовков;
    - проверка подписи HMAC;
    - сверка, что пользователь является оператором.
- Локальный режим:
  - при запуске на `localhost` / `127.0.0.1` и `initData == "dev"`:
    - Mini App общается с API как отдельный owner `local:<operator_id>`;
    - это используется для локального отладки UI без реального Telegram.

В v2 фронтенд не меняет схему auth, только добавляет новые способы отображения и навигации на основе тех же заголовков/кусков данных.

---

## 4. Чётко не реализуемое в v2 (бэкенд)

- **Inbox / «Лента»**:
  - нет отдельной таблицы Inbox;
  - нет статуса `inbox`, `processed`, `archived` у идей;
  - нет эндпоинтов `/api/inbox` или `/api/ideas?status=...`.
  - нижняя иконка «Лента» на фронте — исключительно визуальная заглушка.

- **Статистика / сводка**:
  - нет `/api/stats`, агрегатов по полкам, источникам или периоду;
  - любые визуальные «сводки» в будущем потребуют отдельного проектирования API и, вероятно, индексов/кэшей.

- **People / пользователи**:
  - нет таблиц/полей под People, аватары, роли;
  - любые аватарки и стопки в UI — чистый декор без бэкенда.

---

## 5. Миграции и тесты

- **Миграции БД**:
  - в v2 не добавляются новые таблицы и поля;
  - миграций schema‑уровня не требуется.

- **Тесты**:
  - `tests/test_web.py`, `tests/test_db.py`, `tests/test_shelves.py` остаются источником правды по поведению API;
  - любые правки фронта должны проходить существующие API‑тесты без изменений;
  - при появлении новых тестов UI (например, для горизонтального скролла или подсказочных чипов), они не должны требовать нового API.
